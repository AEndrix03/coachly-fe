# 13 — Localizzazione, formati e unità

ADR-002: **ARB + `gen_l10n`.**

Ci sono **due** problemi di localizzazione distinti, e confonderli è la ragione
per cui oggi ne esistono due sistemi paralleli:

1. i **testi della app** — ARB;
2. i **testi dei dati** — tabella `i18n` nel database.

## 1. Testi della app

### Stato attuale

`app_strings.dart` è una mappa `const` di 2080 righe. In parallelo esiste un
`_t(context, en:, it:)` scritto inline, con 85 occorrenze nel solo
`workout_builder_widgets.dart` e 71 in `create_workout_flow.dart`. Due sistemi,
di cui uno invisibile a qualsiasi strumento.

Nessuno dei due supporta plurali, e non esiste modo di sapere se una chiave manca
in una lingua.

### Target

```yaml
# l10n.yaml
arb-dir: lib/l10n
template-arb-file: app_en.arb
output-localization-file: app_localizations.dart
nullable-getter: false
```

Accesso via extension:

```dart
context.l10n.workoutCompleted
context.l10n.setsCompleted(count)
```

### Naming delle chiavi

`<area><Concetto><Variante>`, camelCase:

```
workoutListEmptyTitle
workoutListEmptyAction
exerciseDetailMusclesTab
activeWorkoutRestRemaining
commonRetry
commonCancel
errorNetworkTitle
```

Il prefisso `common` è riservato a ciò che compare in almeno tre aree diverse.

### Plurali e interpolazione

Sempre ICU, mai concatenazione:

```json
{
  "setsCompleted": "{count, plural, =0{Nessuna serie} =1{1 serie} other{{count} serie}}",
  "@setsCompleted": { "placeholders": { "count": { "type": "int" } } }
}
```

Costruire `"$count esercizi"` a mano è vietato: in italiano e inglese sembra
funzionare, e smette di funzionare alla terza lingua.

### Regole

1. Nessuna stringa letterale user-facing nei widget. Verificato dal lint
   `no_hardcoded_strings`.
2. `_t(context, en:, it:)` viene eliminato completamente.
3. `app_en.arb` è il template: ogni chiave nuova nasce lì.
4. Un test verifica la **parità delle chiavi** fra `en` e `it`.
5. Un test verifica che non esistano **chiavi orfane**.
6. I componenti del design system non traducono: ricevono testo già localizzato
   (`10-components.md`).
7. Nessuna chiave contiene markup o formattazione.

## 2. Testi dei dati

Nome, descrizione, consigli ed errori comuni degli esercizi arrivano dal
catalogo come mappe locale → testo. Non sono chiavi ARB: sono dati.

Vivono nella tabella `i18n(entity_type, entity_id, field, locale, value)`
descritta in `04-data-layer.md`.

**Il bundle spedisce `it` ed `en`.** Sono testi: il costo in byte è trascurabile
rispetto ai media, e in cambio il cambio lingua è istantaneo e offline. Non si
scarica una lingua al volo.

### Catena di fallback

Una sola, centralizzata, mai reimplementata in una feature:

```
<lang>_<country>  →  <lang>  →  en  →  prima disponibile  →  ''
```

Oggi questa logica è duplicata in almeno tre punti (`fromI18n`, `_localized`,
`_localizedList`) con comportamenti leggermente diversi.

### Testi generati dall'utente

Nomi di workout ed esercizi custom **non si traducono**: sono testo dell'utente,
si mostrano come sono. In `i18n` stanno con la locale in cui sono stati scritti.

## 3. Formati

Sempre via `intl`, mai a mano.

| Cosa | Come |
|---|---|
| Date | `DateFormat.yMMMd(locale)` |
| Ore | `DateFormat.Hm(locale)` — mai `HH:mm` hardcoded |
| Durate | formatter dedicato: `1:30`, `45s`, `1h 20m` |
| Numeri | `NumberFormat(locale)` — il separatore decimale cambia |
| Percentuali | `NumberFormat.percentPattern(locale)` |

Il separatore decimale è il caso che morde: `62.5` kg in italiano si scrive
`62,5`, e la tastiera numerica deve accettare entrambi.

## 4. Unità di misura

È localizzazione a tutti gli effetti, e oggi non esiste.

| Grandezza | Unità | Preferenza |
|---|---|---|
| Carico | kg / lb | preferenza utente, default dalla locale |
| Distanza | m / ft | idem |
| Peso corporeo | kg / lb | segue il carico |
| Durata | secondi | non localizzabile |
| Intensità | RIR / RPE / %1RM | preferenza utente |

Regole:

1. **Il database memorizza sempre in unità canonica** (kg, metri, secondi) più
   l'unità di *inserimento*. La conversione è di presentazione: cambiare unità
   non deve mai riscrivere lo storico.
2. La conversione vive in `core/units/`, mai in un repository.
3. Nessun repository costruisce stringhe. Oggi `_buildWeightLabel` produce
   `"75kg"` **dentro** `WorkoutPageRepositoryImpl`: formattazione nel data layer,
   non localizzabile e non testabile.
4. `"3x10"`, `"90s"`, `"75kg"` si costruiscono nella presentazione, da numeri.

## Migrazione

| Fase | Cosa |
|---|---|
| 1 | `l10n.yaml`, ARB vuoti, extension `context.l10n` |
| 2 | Conversione automatica delle ~700 chiavi di `app_strings.dart` |
| 3 | Estrazione manuale dei `_t(…)` inline, feature per feature |
| 4 | Test di parità e chiavi orfane in CI |
| 5 | Lint `no_hardcoded_strings` in errore sui file toccati |
| 6 | Rimozione di `app_strings.dart` |

La fase 3 è la più lunga: sono le feature del workout builder, che sono anche i
file più grandi del progetto. Si fa insieme alla loro scomposizione
(`10-components.md`), non come passaggio separato.
